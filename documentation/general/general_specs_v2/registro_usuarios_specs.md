# Registro de Usuarios — Technical Requirements

**Scope:** Administración > Registro de Usuarios (admin only)
**Date:** 10 Nov 2026
**Mockup (visual reference):** https://claude.ai/artifact/QX3Fopa32TzA3qcag3W6eJ
**UI conventions:** `ui_notes.md` v2.1.1 + `ui_notes_improved.md` v1.0

| # | Requirement | Depends on |
|---|---|---|
| TR-1 | Login Event Capture and Data Layer Redesign | — |
| TR-2 | Resumen de Clientes (overview view) | TR-1 |
| TR-3 | Detalle de Cliente (per-client view) | TR-1, TR-2 |

TR-1 ships first. TR-2 and TR-3 can be built against fixture files that follow the TR-1 schema while TR-1 is in progress.

> **Mockup caveat:** the mockup was drawn before it was confirmed that `capstone_user` belongs to the **Capstone** client. In the mockup it is shown as internal. Treat its figures as illustrative only, not as expected values.

## Shared Definitions

| Term | Definition |
|---|---|
| **Event** | One successful login, stored as one record (TR-1). |
| **Client** | An entry in `clients.json`. Users belong to at most one client. |
| **Internal user** | A user with `user_type = internal` (team accounts, no client). |
| **Display timezone** | A single configurable timezone used to show times and to bucket events into days. Storage is always UTC. **Default to be confirmed (see Open Items).** |
| **Period** | Inclusive date range chosen in the **Período** filter, evaluated in the display timezone. Default: last 30 calendar days including today. |
| **Previous period** | The range of equal length immediately before the period. |
| **Active user** | A user with ≥ 1 event in the period, after filters. |
| **Active client** | A client with ≥ 1 event from any of its users in the period, after filters. |
| **Registered user / client** | A user / client listed in the registry files (TR-1, item 4). |

## Technical Requirement 1 — Login Event Capture and Data Layer Redesign

### Context

Today, every successful login reads the whole user-log parquet file, modifies it, rewrites it and uploads it to S3. The behavior is undocumented. Problems:

- Two simultaneous logins can overwrite each other, so events can be lost.
- Cost and latency grow with file size.
- The data only supports counts per user and environment. Environment is sometimes `unknown`, and there is no client attribution.

The dashboard has no database access, so all data must remain files on S3 (parquet or JSON).

This requirement **replaces** the read-modify-write flow with an append-only event log, a daily parquet compaction, a reference registry and a single data-access layer for the dashboard.

### Required Changes

1. **Document the current implementation (prerequisite).**
   Where: repository docs.
   Before changing code, record the legacy log's S3 key, parquet schema (columns and types), the code path that writes it, and what causes `environment = unknown`. This feeds item 7.

2. **Define the login event.**
   Where: the successful-authentication path of the login handler.
   Current: read file, modify, rewrite, upload.
   Expected: build one event with the fields below and write it as one object (item 3).

   | Field | Type | Rule |
   |---|---|---|
   | `schema_version` | int | `1` |
   | `event_id` | string | ULID or UUIDv4, unique, generated by the writer |
   | `event_type` | string | Always `login` in v1 |
   | `timestamp_utc` | string | ISO-8601 UTC with milliseconds, generated server-side at authentication time |
   | `username` | string | As authenticated, case preserved |
   | `user_type` | string | `client` \| `internal` \| `unmapped`, resolved from `users.json` at write time |
   | `client_id` | string \| null | From `users.json`. `null` for internal and unmapped users |
   | `environment` | string | `production` \| `development` \| `unknown`, from deployment configuration, never from the request |
   | `source` | string | `live` for new events, `legacy_migration` for migrated rows |

3. **Store raw events as one JSON object per event.**
   Where: S3, in the bucket and prefix already used for the current user-log file.
   Key: `auth_events/raw/dt=YYYY-MM-DD/<YYYYMMDDTHHMMSSmmmZ>_<event_id>.json`, where `dt` is the UTC date of `timestamp_utc`.
   - The login path performs a single PUT to a new unique key. It must not read, list or overwrite any existing object under `auth_events/`.
   - The write must not block or delay the login response.
   - On failure, retry up to 3 times with backoff. After the final failure, log an ERROR containing the full event payload so it can be replayed.

4. **Add the reference registry.**
   Where: S3, `auth_registry/clients.json` and `auth_registry/users.json`.
   - `clients.json`: `[{ "client_id": "cda", "display_name": "CDA", "active": true }]`
   - `users.json`: `[{ "username": "cda_user", "user_type": "client", "client_id": "cda" }]`. It must list **every** registered user, including users who never logged in.
   - Initial content: Appendix A.
   - Both files are maintained manually (edit and upload). No admin UI is in scope.
   - The login handler loads `users.json` with an in-memory cache (TTL 5 min, configurable). If a reload fails, keep the last good copy. If it was never loaded, write `user_type = unmapped`.

5. **Compact raw events into daily parquet.**
   Where: a scheduled process (location to be decided, see Open Items).
   Output: `auth_events/daily/dt=YYYY-MM-DD/events.parquet`, one file per UTC day, sorted by `timestamp_utc`, with the same columns as the event and typed columns (`timestamp_utc` as UTC timestamp).
   - Runs at least once per day. Each run (re)compacts every UTC day before today that has raw objects, plus the last 3 days, to absorb late events.
   - Compacting a day = deduplicate (existing daily rows ∪ raw rows) by `event_id`, validate the schema, then overwrite the daily file with a single PUT.
   - Raw objects are deleted only after the daily file is verified (row count equals unique event count) **and** the raw retention window has passed. Default retention: 7 days, configurable.

6. **Provide one data-access layer for the dashboard.**
   Where: the dashboard's data module.
   Expected: one function or module that, given a date range and optional environment, returns a normalized table of events with the schema above and timestamps already converted to the display timezone.
   - It reads daily parquet for compacted days and raw JSON for days not yet compacted.
   - It loads UTC partitions covering the range ±1 day, then filters by the display-timezone range.
   - It deduplicates by `event_id` on every read.
   - It caches results in memory (TTL 60 s, configurable) and exposes the load time (used for "Última actualización").
   - It also exposes the registry (clients and users).
   - TR-2 and TR-3 must use only this layer. No other code reads `auth_events/` or `auth_registry/`.

7. **Migrate legacy data and cut over.**
   Where: one-off script plus release plan.
   - Convert legacy rows into events with `source = legacy_migration`. `event_id` must be deterministic (for example a hash of the row content plus its position) so the migration is idempotent. `user_type` and `client_id` are resolved from the registry at migration time. `environment` is preserved as stored, including `unknown`.
   - If legacy rows have no usable timestamp, report that in the migration output and store them under `auth_events/daily/dt=legacy/events.parquet`. Time-based views exclude them.
   - After migration, archive the legacy file unchanged under `auth_events/legacy/`. Do not delete it.

8. **Remove the legacy path.**
   The old read-modify-write code and the old "Inicios de sesión por usuario" data loading are removed in the same release as the cutover. The legacy flow and the new flow must not run in parallel.

### Functional Rules

- Capture failure must never make a login fail or noticeably slower.
- One login = exactly one event. Concurrent logins always produce distinct objects.
- `environment` comes from the deployment configuration of the running instance. With correct configuration, no new event has `unknown`. Historical `unknown` values remain valid.
- No personal data is stored beyond `username` (no IP, device or user agent).
- A user missing from `users.json` is recorded as `unmapped`. It must not be dropped or blocked.
- Client attribution is the value stored in the event at write time. Changing a user's client in the registry affects future events only.
- Least privilege: the login handler needs write access to `auth_events/raw/` and read access to `auth_registry/`. The dashboard needs read and list access to both prefixes. The compaction process needs read, write and delete access to `auth_events/`.
- Existing admin-only access control for the Registro de Usuarios module remains unchanged.

### Acceptance Criteria

- [ ] The legacy schema and writer are documented in the repo.
- [ ] A successful login creates exactly one new JSON object under `auth_events/raw/dt=<UTC date>/`, and the login path performs no read, list or overwrite of existing objects.
- [ ] 50 simultaneous logins produce 50 distinct objects and no lost events.
- [ ] With S3 unavailable, the login still succeeds and an ERROR with the full payload is logged after 3 retries.
- [ ] Every event contains all fields in the schema, with `timestamp_utc` in UTC.
- [ ] In production and development deployments, new events carry `environment = production` and `development` respectively, never `unknown`.
- [ ] A login by `capstone_user` is stored with `user_type = client` and `client_id = capstone`.
- [ ] A login by a user absent from `users.json` is stored with `user_type = unmapped` and `client_id = null`.
- [ ] Running compaction twice for the same day yields an identical daily parquet. A raw event arriving after the first run is included by the next run.
- [ ] The data-access layer returns each `event_id` once, even when it exists in both raw and daily storage.
- [ ] After migration, per-user and per-environment counts equal those in the legacy file at cutover.
- [ ] The legacy file is archived unchanged, and the old write path no longer exists in the codebase.
- [ ] TR-2 and TR-3 read data only through the data-access layer.

## Technical Requirement 2 — Resumen de Clientes (Overview View)

### Context

The current Administración > Registro de Usuarios view is a single bar chart of logins per user, split by environment. It cannot show which clients are engaged, growing or fading. This requirement **replaces** that view with a simple, client-centric overview. It is the default view of the route and the entry point to the per-client view (TR-3).

### Required Changes

1. **Replace the view.**
   Where: Administración > Registro de Usuarios.
   The existing chart view is removed. Resumen de Clientes becomes the default view. Admin-only access is unchanged.

2. **Header.**
   - Breadcrumb: `Administración › Registro de Usuarios`.
   - H1: `Registro de Usuarios`.
   - Subtitle: `Comportamiento de los clientes en la plataforma · Última actualización: <D Mmm YYYY, HH:mm>`. The timestamp is the data-access layer's load time.

3. **Filters (one row, each with a visible label).**

   | Control | Type | Options | Default |
   |---|---|---|---|
   | Período | select | Últimos 7 Días, Últimos 30 Días, Últimos 90 Días, Personalizado | Últimos 30 Días |
   | Ambiente | select | Todos, Producción, Desarrollo, Desconocido | Todos |
   | Incluir Usuarios Internos | checkbox | on / off | off |

   Período and Ambiente are shared with TR-3, so navigating between views keeps them.

4. **KPI tiles (3, equal height).**
   - **Inicios de Sesión de Clientes**: event count in the period. A chip shows the change versus the previous period, and the caption reads `vs. <N> días anteriores (<previous count>)`. When *Incluir Usuarios Internos* is on, the label becomes `Inicios de Sesión` and the count includes internal users.
   - **Clientes Activos**: count of active clients. Chip: percentage. Caption: `de <M> clientes registrados`. Internal users are never counted as a client.
   - **Usuarios Activos**: count of active client users. Chip: percentage. Caption: `de <K> usuarios de clientes registrados`.

5. **Clients table** (title `Clientes`, with the period range as a caption).

   | Column | Content |
   |---|---|
   | Cliente | `display_name` as a link to TR-3 |
   | Inicios de Sesión | Count plus a bar proportional to the largest count in the table. Default sort: descending |
   | vs. `<N>` Días Previos | Chip with arrow and signed %, e.g. `▲ +13,1%`, `▼ −4,3%` |
   | Usuarios Activos | `<active> de <registered>` |
   | Tendencia | Sparkline of daily events across the period |
   | Último Acceso | Relative time of the client's most recent login |
   | (action) | `Ver Detalle ›` link, same target as the client name |

   - One row per `active = true` client in `clients.json`, including clients with 0 events.
   - When *Incluir Usuarios Internos* is on, add one extra row `Equipo Interno`, pinned last. It links to TR-3 with `client_id = internal`.
   - Footer: `Seleccione un cliente para ver sus usuarios, días de actividad y registro de accesos.`

6. **Daily chart** (title `Inicios de Sesión de Clientes por Día`).
   - One bar per day with total events, a single series, integer y-axis ticks, and an x-axis label about every 5 days.
   - Tooltip: `<Ddd> <D Mmm> · <n> inicios de sesión`.
   - Caption: `Número de inicios de sesión por día, todos los clientes`.
   - Ranges over 90 days use weekly buckets (Mon–Sun) to stay legible. This is an implementation decision.

7. **Footnotes.**
   - When internal users are hidden and have events in the period: `Excluye <n> inicios de sesión de usuarios internos.`
   - If any `unmapped` user has events in the period: `<n> inicios de sesión de usuarios sin cliente asignado: <usernames>.`

### Functional Rules

- All metrics respect Período and Ambiente. Event counts use each event's `client_id` as stored.
- **Change vs. previous period** = `(current − previous) / previous × 100`, one decimal.
  - If previous = 0 and current > 0, show `Nuevo`.
  - If both are 0, show `–`.
  - A change of exactly 0 shows `0,0%` with no arrow.
- **Último Acceso** uses the full event history and ignores Período, but respects Ambiente. Format:
  - under 1 h: `Hace N min`
  - under 24 h: `Hace N h`
  - previous calendar day: `Ayer, HH:mm`
  - otherwise: `Hace N días`
  - never logged in: `Sin accesos`
- Percentages in chips are rounded to the nearest integer.
- Numbers use es-CL formatting: `.` for thousands and `,` for decimals (e.g. `1.450`, `+13,1%`).
- Color follows `ui_notes_improved.md`:
  - These metrics are not severity scores, so they use the neutral blue palette and never the red/amber/green severity palette.
  - Increases use a blue tint, decreases a gray tint, and the arrow plus sign always accompany the color.
  - The left-border-accent card pattern is not used. KPI tiles use tinted icon badges and `h-100`.
- All labels use Title Case and correct Spanish accents. All filters are real labelled controls, and links are real `<a href>` elements.
- Empty period (no events): KPIs show 0, the chart shows `Sin inicios de sesión en el período`, and table rows show 0 with `–` as the change.

### Acceptance Criteria

- [ ] Opening Administración > Registro de Usuarios shows Resumen de Clientes. The old chart is gone. Non-admin users cannot reach it.
- [ ] Defaults on load: Últimos 30 Días, Todos, internal users excluded.
- [ ] Changing Período or Ambiente updates the KPIs, table, sparklines and chart consistently.
- [ ] Total events in the table (internal excluded) equal the first KPI.
- [ ] A client with 0 events in the period still appears in the table, with 0 events and its `Último Acceso`.
- [ ] Checking *Incluir Usuarios Internos* adds the `Equipo Interno` row last, includes internal events in the first KPI and the chart, and leaves `Clientes Activos` unchanged.
- [ ] The change chip follows the rules for previous = 0, both 0 and exactly 0.
- [ ] Clicking a client name or `Ver Detalle ›` opens TR-3 for that client with Período and Ambiente preserved.
- [ ] Unmapped-user events are not dropped silently; the footnote appears.
- [ ] No red, amber or green is used for any value in this view.
- [ ] Tab navigation reaches every filter and link, and every filter has a visible label.

## Technical Requirement 3 — Detalle de Cliente (Per-Client View)

### Context

TR-2 compares clients. Admins also need to see how one client behaves: who logs in, how often, when, and how that is changing. This requirement **adds** a per-client view reached from the Resumen de Clientes table. It uses the same filters, data layer and visual conventions as TR-2.

### Required Changes

1. **Addressable view.**
   Where: Administración > Registro de Usuarios, client sub-view.
   - The view is addressed by a URL carrying the client, so it can be bookmarked and shared (for example `?client=<client_id>`; the exact format follows the app's existing routing).
   - `client_id = internal` is valid and shows internal users, with H1 `Equipo Interno`.
   - An unknown `client_id` shows `Cliente no encontrado` and a link back to Resumen de Clientes.
   - Admin-only access is unchanged.

2. **Header.**
   - Breadcrumb: `Administración › Registro de Usuarios › <display_name>`. The middle item links to Resumen de Clientes.
   - H1: the client's `display_name`.
   - Subtitle: `Comportamiento de inicio de sesión del cliente · Última actualización: <D Mmm YYYY, HH:mm>`.
   - A link styled as a button, `‹ Todos los Clientes`, returns to Resumen de Clientes.

3. **Filters.** Cliente (select), Período and Ambiente (same options and defaults as TR-2).
   - Cliente lists every `active = true` client plus `Equipo Interno`. Changing it navigates to that client's view.
   - Período and Ambiente are shared with TR-2.

4. **KPI tiles (4, equal height).**
   - **Inicios de Sesión**: count with a chip for the change versus the previous period, and the caption `vs. <N> días anteriores (<previous count>)`.
   - **Usuarios Activos**: active users, with a percentage chip and the caption `de <registered> usuarios registrados`.
   - **Días con Actividad**: days with ≥ 1 event, with a percentage chip and the caption `de <N> días del período`.
   - **Último Acceso**: relative time, with a chip showing the absolute date and time (e.g. `Vie 6 Nov, 16:12`) and the caption `usuario <username>`.

5. **Daily chart** (title `Inicios de Sesión por Día`).
   - Bars are stacked by user, with a legend labelled `Usuario`, the user with the most events at the bottom, and a tooltip listing each user's count.
   - At most 5 users are drawn individually. Any others are grouped as `Otros`.
   - Series colors differ in lightness (blue shades, `Otros` in gray) so they are distinguishable without hue alone.
   - Caption: `Número de inicios de sesión por día, apilados por usuario`.
   - The same weekly-bucket rule as TR-2 applies above 90 days.

6. **Users table** (title `Usuarios del Cliente`).

   | Column | Content |
   |---|---|
   | Usuario | `username` |
   | Producción / Desarrollo | Event counts, `–` when 0. Column headers carry the environment's color square |
   | Desconocido | Shown only if any `unknown` event exists in the current selection |
   | Total de Inicios | Count plus a proportional bar. Default sort: descending |
   | Días Activos | Days with ≥ 1 event for that user |
   | Último Acceso | Same format as TR-2 |

   - Rows include **all** registered users of the client, including those with 0 events (total `0`, `Último Acceso` per the rule).
   - Footer: `<active> de <registered> usuarios registrados tuvieron inicios de sesión en el período.`

7. **Heatmap** (title `Actividad por Día y Hora`).
   - Rows are Lun–Dom and columns are twelve 2-hour blocks (`00`, `02`, … `22`), in the display timezone.
   - Each cell shows its event count (empty when 0).
   - There are 5 intensity levels relative to the largest cell in the selection (0, ≤ 15%, ≤ 35%, ≤ 65%, > 65%), with text contrast ≥ 4.5:1.
   - Tooltip: `<Ddd> HH:00–HH:00 · <n> inicios`.
   - A `Menos … Más` legend, and the caption `Inicios de sesión por bloque de 2 horas · Hora local`.

8. **Recent log** (title `Registro Reciente`).
   - Columns: Fecha y Hora (`D Mmm YYYY, HH:mm`), Usuario, Ambiente (color square plus label).
   - It shows the last 6 events in the selection, newest first.
   - Footer: `Mostrando 6 de <total> registros` and a `Ver Registro Completo` link.

9. **Full log.**
   The `Ver Registro Completo` link opens a paginated table (25 rows per page, newest first) with the same columns, scoped to the client, Período and Ambiente, and a link back to this view. No export.

### Functional Rules

- All figures respect Período and Ambiente and use the same definitions as TR-2, including change vs. previous period and `Último Acceso` (full history, Ambiente-aware).
- Environment colors are non-severity: Producción `#1e3a8a`, Desarrollo `#60a5fa`, Desconocido `#cbd5e1` with a `#94a3b8` border. Color is always paired with a text label.
- A client with no registered users shows `Sin usuarios registrados` in the users table.
- A client with no events in the period shows KPIs at 0 and `Sin inicios de sesión en el período` in the chart, heatmap and log.
- The same visual rules as TR-2 apply:
  - neutral blue for non-severity metrics
  - no left-border-accent cards
  - Title Case and Spanish accents
  - labelled controls and real links
  - es-CL number formatting

### Acceptance Criteria

- [ ] Clicking a client in Resumen de Clientes opens its view, and the URL identifies the client.
- [ ] Opening the URL directly (or reloading) shows the same view.
- [ ] `‹ Todos los Clientes` and the breadcrumb return to Resumen de Clientes with filters preserved.
- [ ] Changing the Cliente select navigates to that client's view.
- [ ] `Inicios de Sesión` equals the client's row in TR-2 for the same filters.
- [ ] The chart's daily totals equal the sum of the per-user counts in the users table.
- [ ] A registered user with no events in the period appears in the users table with a total of 0.
- [ ] The `Desconocido` column appears only when the selection contains `unknown` events.
- [ ] Heatmap cell sums equal the total event count in the selection, and its bucketing uses the display timezone.
- [ ] The recent log shows the 6 newest events and `Ver Registro Completo` opens the paginated log with the same scope.
- [ ] Unknown `client_id` shows `Cliente no encontrado`; `internal` shows `Equipo Interno`.
- [ ] The view is unreachable for non-admin users.

## Scope Notes

**In scope:** login activity (who, when, which environment, which client).
**Out of scope:** in-platform activity (pages or features used), registry management UI, alerting.

### Optional Considerations (not part of the mandatory scope)

- **Failed-login events** (`event_type = login_failed`), useful for security review. The schema already carries `event_type`.
- **`is_test` flag on users** to exclude test accounts such as `cda_tester` from client metrics.
- **IP and device capture** (adds personal data; needs a decision).
- **CSV export** of the full log.
- **Inactivity indicator** for clients with no logins for N days.

## Open Items

1. **Display timezone** default (storage is UTC).
2. **Mapping confirmation** for the accounts marked *Assumed* or *Inferred* in Appendix A. Only `capstone_user → capstone` is confirmed.
3. **Legacy schema.** Output of TR-1 item 1. It determines whether legacy rows can appear in time-based views.
4. **Where compaction runs** (scheduled task, serverless job or inside the app) and who owns it.
5. **Defaults to confirm:** raw retention 7 days, registry cache 5 min, data cache 60 s.
6. **Registry completeness.** The full list of registered users (including those who never logged in) and registered clients. The mockup showed one extra client with no activity as a placeholder.
7. **Test accounts.** Whether `cda_tester` should count as CDA activity (see Optional Considerations).
